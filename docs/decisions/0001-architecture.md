# ADR-001 ~ ADR-006: 架构决策汇总

## ADR-001: 单进程而非双进程
- **背景**：音频、ASR、UI 之间需要毫秒级时间对齐。
- **决策**：单一 `Earcue.exe`，多线程运行（Audio 采集、Pipeline、LLM IO、UI 线程）。
- **理由**：打包简单、通信延迟为零。

## ADR-002: 用流式 ASR，不用 Whisper 攒段
- **背景**：Whisper 类模型非流式，会导致 3~5 秒甚至更长的攒段延时。
- **决策**：流式 Zipformer / Paraformer 架构。
- **理由**：说话过程中增量出字，句末 200ms 内完成识别。

## ADR-003: 触发闸门用“流的来源”，不用语义判断
- **背景**：防止系统回答自己提出的问题。
- **决策**：疑问判定只订阅环流（对方输出声音）；麦克风流永不触发，仅进入 90 秒上下文缓冲区。
- **理由**：物理级隔离，彻底根绝自己说话引起的误答。

## ADR-004: 双流非对称模型
- **决策**：环回流使用高精度识别，麦克风流使用轻量级识别。
- **理由**：节约 CPU 资源，麦流少许错字不影响提问触发与回答精准度。

## ADR-005: 回声先门控，后 AEC
- **决策**：V1 阶段使用半双工门控（环流有能量时降低或丢弃麦流采集）；V2 引入完整 AEC3。
- **理由**：保证 6 周按期交付。

## ADR-006: 字幕用分层窗口，不用 Electron
- **决策**：WPF + Win32 原生互操作。
- **理由**：极低内存与 CPU 占用，天然支持 `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` 防会议屏幕共享泄露。
