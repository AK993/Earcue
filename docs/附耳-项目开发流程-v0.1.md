## 1. 项目定义

### 1.1 一句话

会议里别人向你提问时，在屏幕角落递给你一句 40 字以内、可以直接说出口的话。

### 1.2 一个具体的使用画面

> 你在腾讯会议上做方案汇报。对方产品经理问："那你们这个灰度策略怎么保证回滚？"
> 你余光扫到屏幕右下角浮出一张半透明卡片：
> 　　`[对方] 那你们这个灰度策略怎么保证回滚？`
> 　　**按 5% 分批，每批观察 30 分钟，异常率超 1% 立即回滚上一版本**
> 你照着这个思路答完，卡片在 20 秒后自动淡出。

### 1.3 范围红线（明确不做）

- 会议纪要、全文转录、导出
- 对方参会者级的说话人分离
- TTS 代你说话
- 会后回放、知识库沉淀
- 移动端、macOS / Linux
- 团队协作、云端同步

### 1.4 发布门槛（v1.0 必须全部满足）

| 指标 | 目标值 | 测量方式 |
|---|---|---|
| 端到端首字延迟 | P50 ≤ 2.0s ／ P90 ≤ 3.0s | 从"对方说完最后一个字"到卡片出现首字 |
| 触发精准率 | ≥ 85%（宁可漏答，不可乱答） | 30 段真实会议回放人工标注 |
| 触发召回率 | ≥ 60% | 同上 |
| 稳定性 | 连续 4 小时会议零崩溃、零断流 | 长稳测试 |
| 资源占用 | CPU 平均 ≤ 20%，内存 ≤ 1.5 GB | 主流轻薄本实测 |
| 隐私 | 无音频落盘/外传；共享屏幕不可见 | 抓包 + 五款会议软件实测 |
| 安装 | 签名安装包，SmartScreen 无红色警告 | 干净虚拟机 |

## 2. 技术架构

### 2.1 数据流

```
┌──────────────────────── 单进程 Earcue.exe ────────────────────────┐
│                                                                    │
│  Audio Thread                       ASR Worker × 2                 │
│  ┌──────────────┐   环形缓冲    ┌──────────────────┐               │
│  │ WASAPI 环回  │──────────────▶│ 识别器 A（大模型）│──┐            │
│  │  (对方)      │   16k mono    └──────────────────┘  │            │
│  └──────────────┘                                     │            │
│  ┌──────────────┐   回声门控    ┌──────────────────┐  │ 带角色标注 │
│  │ WASAPI 麦克风│──────────────▶│ 识别器 B（小模型）│──┤ 的转录流   │
│  │  (我)        │               └──────────────────┘  │            │
│  └──────────────┘                                     ▼            │
│         ▲                                    ┌──────────────────┐  │
│         │ 沉默填充 / 设备监听 / 重采样       │ Pipeline         │  │
│         │                                    │ VAD→断句→疑问判定│  │
│                                              └────────┬─────────┘  │
│                                                       │ 触发事件   │
│                                                       ▼            │
│                                              ┌──────────────────┐  │
│                                              │ LLM Client (SSE) │  │
│                                              └────────┬─────────┘  │
│                                                       │ 流式文本   │
│                                                       ▼            │
│                                              ┌──────────────────┐  │
│                                              │ Overlay (WPF)    │  │
│                                              └──────────────────┘  │
└────────────────────────────────────────────────────────────────────┘
```

### 2.2 进程与线程模型

**单进程，多线程**（理由见 ADR-001）：

| 线程 | 职责 | 实时性 |
|---|---|---|
| Audio Capture | WASAPI 回调取帧，写入环形缓冲；按 10ms 节拍补静音帧 | 硬实时，不可阻塞 |
| ASR-A / ASR-B | 两个独立识别器，互不阻塞 | 软实时 |
| Pipeline | VAD → 断句 → 疑问判定 → 组上下文 | 软实时 |
| LLM IO | SSE 流式读取，异步 | 网络态 |
| UI | WPF 渲染、热键、托盘 | 主线程，不可做重活 |

**铁律**：音频回调里不做任何分配、不加锁、不写日志、不做重采样。只做 memcpy 到环形缓冲，其余交给工作线程。

### 2.3 可测试性设计（第一天就要定下来）

三个接口，让整条链路可以脱离硬件离线回放：

```csharp
interface IAudioSource  { event Action<AudioFrame> FrameReady; }   // WasapiLoopbackSource / FileSource
interface IAsrEngine    { IAsyncEnumerable<AsrPartial> Push(AudioFrame f); }
interface ILlmClient    { IAsyncEnumerable<string> Ask(Prompt p, CancellationToken ct); }
```

有了 `FileSource`，M2 之后所有联调都在录好的会议音频上跑，不用每次都真开会。这是项目能不能按期交付的关键设计。

### 2.4 技术选型

| 环节 | 选型 | 备选 | 备注 |
|---|---|---|---|
| 语言/框架 | C# / .NET 8 + WPF | Rust + winit、C++ + Qt | C# 调 ONNX Runtime 和 Win32 都很顺 |
| 音频采集 | NAudio（WASAPI） | windows-rs 直接调 COM | 环回建议**定时轮询**，不依赖事件驱动 |
| VAD | Silero VAD（ONNX） | WebRTC VAD | 16k、512 采样一帧，CPU 开销极小 |
| ASR | sherpa-onnx 流式 Zipformer（中英） | FunASR Paraformer 流式 | 真流式、C# 可调、可离线 |
| 断句 | 自研：VAD 停顿 + 最大时长兜底 | — | 不要指望纯静音切分 |
| 疑问判定 | 规则 + 轻量模型二选一 | 纯 LLM 判定 | 先规则，够用就不加模型 |
| LLM | DeepSeek / Qwen / GPT 系 | — | 支持 SSE 流式即可，模型名做成配置 |
| 覆盖窗口 | WPF 分层窗口 + Win32 互操作 | Electron、ImGui | 见 ADR-006 |
| 热键 | RegisterHotKey | 低级键盘钩子 | 钩子易被误判为可疑软件，不推荐 |
| 日志 | Serilog（滚动、按级别） | — | 默认不记录转录文本 |
| 打包 | Inno Setup + 代码签名 | MSIX | MSIX 对 Win10 老版本友好度一般 |
| 崩溃 | 本地 minidump + 可选上报 | — | 上报默认关闭 |

## 4. 阶段详解

### M0 · 立项与需求冻结（1 天）

**任务**
- 确认第 0 章 8 条前提，写进 `docs/decisions/0000-scope.md`
- 确认第 1.4 节发布门槛
- 建仓库、CI（只跑编译 + 单测）、目录骨架
- 选定 3 段真实会议音频作为测试夹具（**注意脱敏**）

**出口标准**：仓库能 `dotnet build` 通过，空 WPF 窗口能起来。

---

### M1 · 技术验证（4 天）

这一步的目的不是"做出功能"，而是**在投入大量代码之前，确认三个致命假设**。每个 spike 都要写结论，失败就改方案，不延期。

#### S1 · 环回采集稳定性（0.5 d）

- **假设**：默认输出设备上能稳定拿到 16k 数据，静音时不会打乱时间轴
- **做法**：最小 demo，把 RMS、包间隔、累计采样数打到控制台
- **观察点**
  1. 会议安静 30 秒时，是否**完全没有数据包**（预期：是）
  2. 补静音帧后，累计采样数是否与墙钟一致（漂移 < 50ms/小时）
  3. 中途切到蓝牙耳机，流是否报错、能否自动重建
  4. 系统静音后，环回给的是全零还是原始信号
- **通过标准**：1 小时无异常，漂移达标
- **失败预案**：改用 WASAPI 回环的定时轮询 + 自建时钟；最坏情况要求用户装虚拟声卡（体验下降，但可用）

#### S2 · 覆盖窗口与捕获排除（1.5 d）

- **假设**：半透明置顶卡片能做到「不抢焦点 + 点击穿透 + 共享时不可见」
- **做法**：一个空窗口，套上扩展样式，用腾讯会议/Teams/Zoom 各自共享全屏验证
- **观察点**
  1. `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` 是否对该版本生效
  2. 共享"窗口"模式与"全屏"模式表现是否一致
  3. 打字时窗口是否抢焦点
  4. 150% 缩放下位置与字号是否正确
- **通过标准**：五款会议软件共享时均不可见
- **失败预案**：对不生效的软件，提供"共享时自动隐藏"策略（检测前台进程）；这是产品兜底，不是技术兜底
- **⚠️ 这是发布门槛，不是可选项**

#### S3 · 端到端延迟（1.5 d）

- **假设**：本地流式 ASR + 云端流式 LLM 能做到 P50 ≤ 2s
- **做法**：录一段自问自答的音频，喂进链路，用时间戳记录每个环节耗时
- **观察点**：采集缓冲、断句等待、ASR 出字、LLM 首 token、渲染，各占多少
- **通过标准**：P50 ≤ 2s
- **失败预案**：砍上下文长度、换更小模型、把"断句等待"从 800ms 压到 400ms（牺牲准确率）

**M1 出口**：`docs/spikes/` 下三份结论，每份一句话：能 / 不能 / 需要什么条件。

---

### M2 · 骨架打通（5 天）

**目标**：屏幕上能实时看到"会议里在说什么"。此阶段不做任何智能。

**任务**
1. 项目分库：`Core / Audio / Speech / Brain / Overlay / App`
2. `WasapiLoopbackSource`：共享模式、16k 单声道、10ms 帧
3. 环形缓冲 + 固定节拍补静音帧（**这是本阶段最容易写错的地方**）
4. 设备变化监听（`IMMNotificationClient`），默认设备切换自动重建
5. 重采样（48k/44.1k → 16k，建议用成熟重采样库，别自己写）
6. `SherpaAsrEngine`：接入流式识别，输出增量文本 + 标点
7. 调试窗口：显示实时文本 + 每段耗时 + 队列深度
8. `FileSource` 实现（离线回放）

**出口标准**
- 用一段 30 分钟真实会议音频回放，文本持续输出，无卡死
- 时间轴漂移 < 50ms/小时
- 拔插耳机三次，采集能自恢复
- 调试窗口显示 ASR 延迟 P50

**风险提示**：不要在 M2 就接 LLM。先让"听"这件事稳，否则后面所有 bug 都会被误判成模型的错。

---

### M3 · 理解层（5 天）

**目标**：把连续文本变成"一个被问到的问题"。

**任务**
1. VAD 接入，产生语音段；丢弃过短（< 0.4s）和音乐型音频
2. 断句器：`静音 ≥ 600ms` 或 `长度 ≥ 10s` 或 `句末标点` 三者取先
3. 疑问句判定 v1（规则）：
   - 疑问词表（吗/呢/什么/怎么/为什么/是否/能不能/请问/如何/多少/哪/有没有）
   - 句末标点或语气词
   - 长度 ≥ 5 字（过滤"嗯？""啊？"）
4. 冷却机制：同一问题 8 秒内不重复触发；连续触发间隔 ≥ 5 秒
5. 上下文组装：最近 90 秒带 `[对方]/[我]` 标注的转录
6. 触发日志（本地，可导出）——这是后面调优的唯一依据

**出口标准**
- 回放 3 段会议（每段 20 分钟），人工标注应触发的问题，计算精准率 / 召回率
- 精准率 ≥ 80%，误触发 ≤ 1 次 / 10 分钟

**调优方法**：先把**所有**触发打出来看，别急着改代码。前 20 条错误样本通常能指出一个系统性缺陷，改那一处比调十个阈值有用。

---

### M4 · 回答层（3 天）

**任务**
1. `OpenAiCompatibleLlmClient`：SSE 流式、首 token 超时 5s、总超时 20s、429/5xx 重试 1 次
2. Prompt v1（结构固定，便于迭代）
3. 输出约束：≤ 40 字、口语、可直接说出口；不确定时必须说"这个我不确定"
4. 去重：与上一张卡片相似度高则不重复展示
5. 失败降级：LLM 不可用时只显示"听到的问题"，不显示错误弹窗

**Prompt 骨架（v1）**

```
你是我的会议助手。我只在屏幕角落看你给的提示，所以答案必须极短。
【我的角色】{用户设置的岗位/负责模块}
【我的立场】{可选：当前项目、已否决的方案}
【最近对话】
[对方] ...
[我] ...
[对方] 那你们这个灰度策略怎么保证回滚？
【要求】
1. 用第一人称、口语，≤ 40 字，像我会说的话
2. 只给一个最可能的答案，不要列举多个方案
3. 证据不足时输出"这个我不确定，建议确认 XX"
```

**出口标准**：10 个真实问题，答案里至少 7 个"可以直接说出口"（自己念一遍判断）。

### M5 · 呈现层（5 天）

**任务**
1. 分层窗口：`WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`
2. `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`，失败时记录并降级
3. 透明度分层：**背景 alpha 可调（0–100%），文字始终不透明**
4. 文字可读性：描边 + 阴影，浅色背景也能看清
5. 定位：默认右下角，可拖动，位置记忆；多显示器与 DPI 变化重算
6. 卡片内容：灰色小字原文 + 亮色大字答案，最多两行
7. 交互：热键（对最近 60s 提问 / 隐藏 / 收起 / 透明度 ±）、托盘菜单、设置页
8. 动效：淡入 120ms，20 秒无操作淡出；新答案替换旧卡片

**出口标准**
- 五款会议软件共享时卡片不可见（复用 S2 的验证脚本）
- 全屏游戏/视频下能显示（无边框窗口模式）
- 打字、拖拽、切窗口时不抢焦点
- 125% / 150% / 175% 缩放下布局正确

### M6 · 稳定与体验（5 天）

## 5. 架构决策记录（ADR）

### ADR-001 单进程而非双进程

- **背景**：音频、ASR、UI 之间需要毫秒级时间对齐
- **决策**：单一 `Earcue.exe`，多线程
- **备选**：C# UI + Python ASR 服务（IPC 传音频，延迟与复杂度上升）；Electron 全栈
- **后果**：打包最简单、延迟最低；代价是放弃 Python 独有模型，只能走 ONNX Runtime 能加载的模型

### ADR-002 用流式 ASR，不用 Whisper 攒段

- **背景**：Whisper 类模型非流式，会议场景需要"说完 1 秒内出字"
- **决策**：sherpa-onnx 流式 Zipformer
- **备选**：FunASR 流式（中文更强，但需额外运行时）；faster-whisper（准确率高、延迟不可接受）
- **后果**：延迟可控；中文专名与行业术语准确率需靠热词表 + 后处理补

### ADR-003 触发闸门用"流的来源"，不用语义判断

- **决策**：疑问判定只订阅环流；麦克风流永不触发
- **后果**：物理上不可能回答自己的提问；无法处理"我替别人转述问题"（可接受）

### ADR-004 双流非对称模型

- **决策**：环流用高精度模型，麦流用轻量模型
- **后果**：CPU 占用可控；麦流的错字只影响上下文，不影响答案正确性

### ADR-005 回声先门控，后 AEC

- **决策**：V1 用半双工门控（环流有能量时丢弃麦流）；V2 再上 AEC3（环流作参考信号）
- **后果**：双讲时丢失我方插话；换来 V1 少两周工作量

### ADR-006 字幕用分层窗口，不用 Electron

- **决策**：WPF + Win32 互操作
- **备选**：Electron/Tauri（透明度易做，但抢焦点、捕获排除、内存占用都更难控）
- **后果**：需要处理 DPI 与多屏；换来最低的资源占用

## 10. 成本估算

**API 成本公式**

```
单次调用 tokens ≈ (上下文窗口字数 × 1.5) + 系统提示 400 + 输出 80
单场会议（1 小时，触发 40 次）≈ 45k 输入 + 3k 输出
```

按各家定价代入，量级通常在"一场会议几毛钱"。真正的风险不是钱，是**触发太频繁导致卡片刷屏**，所以冷却机制比省钱更重要。

**一次性成本**：代码签名证书（EV 约 ¥3000–5000/年）；开发机（有独显更稳，但纯 CPU 也能跑流式 ASR）。

## 11. 上线后度量

**北极星指标**：每周"被采纳的建议数"——用户看到卡片后没有手动收起、且在 10 秒内没有触发追问。

**最小埋点（默认本地统计，用户可选上传）**
- 触发次数 / 采纳次数 / 手动收起次数
- 端到端延迟分布
- ASR 平均置信度
- 崩溃与异常次数

**隐私边界**：埋点不含任何文本内容，只有计数与耗时。
